# План: адресация чатов («текущий чат» под сводкой)

Статус: сделано целиком — пункты 1, 2 и 3. Кнопки живут в
`app/bot/keyboards.py:under_digest`, адресный вопрос — в
`service.answer_question(chat=...)`, пересылка — в `service.send_photos`.
Оставлено как запись решения: здесь написано, почему сделано именно так.

## Корень проблемы

У команд бота нет понятия «текущий чат». `/q` — глобальная команда без
адресата, поэтому веерит вопрос по всем `user.chats`. С двумя чатами это:

- удваивает стоимость и задержку — `fetch_window` + вызов LLM на каждый чат
  (`app/service.py:219-235`, `answer_question`);
- даёт двусмысленность — одна тема в двух чатах приходит двумя ответами,
  непонятно, к какой сводке относилось;
- расходится с моделью в голове — вопрос рождается при чтении сводки *одного*
  чата.

Тот же корень мешает и пересылке фото: фото надо тянуть из конкретного чата.

## Идея-фундамент

Привязать контекст туда, где вопрос возникает — **к самой сводке**. Сводки уже
уходят по одному сообщению на чат (`app/service.py:33`, `_digest_chat`). Значит,
под каждой можно повесить инлайн-кнопки, которые кладут `chat_id` в FSM, и
следующее действие идёт **только в этот чат**.

`/q текст` оставить как «широкий» шорткат по всем чатам — текущее поведение,
для него оно уместно.

## Что делать (по порядку)

1. **Фундамент: «текущий чат» под сводкой.**
   - Инлайн-кнопки под каждым сообщением сводки в `_digest_chat`.
   - Класть `chat_id` выбранного чата в FSM-состояние (рядом с `Asking.question`
     в `app/bot/commands.py:22`).

2. **Адресный вопрос.**
   - Кнопка «❓ Спросить про этот чат» → `service.answer_question`, но по одному
     чату вместо цикла по `user.chats`.
   - Вероятно, добавить в `answer_question` необязательный параметр «конкретный
     чат» и не веерить, когда он задан.

3. **Пересылка фото по запросу.**
   - Кнопка «🖼 Показать фото» под сводкой → переслать последние N фото этого
     чата, каждое с подписью и временем.
   - Сантехника уже есть: `photo_links()` (`app/max_client.py:159`) отдаёт
     `(photo_id, base_url)`; `vision.py` уже качает байты по этому URL.
   - **Важно:** URL живут недолго, MAX подписывает их сроком
     (`app/max_client.py:160`). Тянуть свежим `fetch_window` на месте, ссылки
     не хранить.
   - MVP: не угадывать, к какой строке сводки относится фото (сводка — LLM-проза),
     а просто переслать последние N фото окна чата.
   - Политике «ограниченного распознавания» (`app/vision.py:4`: 22 из 27 фото —
     шум) это не противоречит: там про «не описывать автоматически», а тут
     человек смотрит сам по запросу.
